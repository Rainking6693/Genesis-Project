Solution: Check database size, run ANALYZE, clear old data

Issue: Out of memory
Solution: Reduce buffer sizes (DREAMGYM_MAX_*), clear old trajectories

Issue: Trajectory pool mirroring fails
Solution: Ensure TrajectoryPool uses add_trajectory() method (auto-mirrors)

================================================================================
ARCHITECTURE SUMMARY
================================================================================

FLOW: Agent Execution → TrajectoryPool → Automatic SQL Mirror → Memori

1. Agent executes code/business generation
2. Trajectory created with results, success_score, operator_applied
3. TrajectoryPool.add_trajectory() called
4. Automatic trigger: SQLTrajectoryMirror.record()
5. Memori: MemoriClient.upsert_trajectory()
6. Database: INSERT INTO trajectories (SQLite)
7. WAL journaling ensures durability
8. Concurrent writes handled by RLock + thread-safety
9. Data available for SQL queries and analytics

COMPONENTS:
- DreamGym: Generates 16 synthetic experiences per batch (1.34s)
- HybridBuffer: Maintains 20% real / 80% synthetic ratio
- Curriculum: Progresses from easy → medium → hard
- TrajectoryPool: Tracks execution history, auto-mirrors to SQL
- Memori: SQL-native backend for trajectory storage and analytics
- SQLTrajectoryMirror: Automatic mirroring layer

QUERY PERFORMANCE:
- SELECT by trajectory_id: 15-18ms
- SELECT recent trajectories: 13-15ms
- Full scan (100K records): <100ms
- Concurrent writes (10+ agents): No contention (WAL)
